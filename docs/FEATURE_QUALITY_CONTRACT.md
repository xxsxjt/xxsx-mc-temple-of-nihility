# 虚无圣殿功能质量契约

> 更新日期：2026-07-19  
> 目标：Minecraft 26.2 / NeoForge 26.2.0.7-beta  
> 当前版本：1.0.0-beta.3  
> 依据：MC 开发 skill v4.2 的纵向闭环、模组原生设计、可学习性、扩展性与回归要求

本文是当前阶段的执行契约。开发单位不再是“又注册了多少物品”，而是“一个系统是否形成可发现、可操作、可验证、可恢复、可扩展的完整闭环”。

## 一、统一完成标准

每个核心系统必须同时满足以下层面；缺少任一关键层时只能标为“部分实现”。

| 层面 | 本项目要求 |
|------|------------|
| 玩家闭环 | 有明确入口、合法操作、真实状态变化、结果反馈、失败原因和恢复方法 |
| 权威状态 | 服务端拥有状态与结算；客户端只提交意图并显示同步结果 |
| 模组原生实现 | 使用命名明确的状态、服务、验证器、事件和 payload，不用命令字符串或原版 Buff 冒充核心机制 |
| 玩家表面 | 配方/发现、GUI、提示、圣典、JEI、模型、贴图、动作、特效、音效和双语文本与真实行为一致 |
| 可学习性 | 玩家能在游戏内看到正确示例、阻塞原因、修复方式和下一步，不依赖外部教程猜操作 |
| 韧性 | 处理连点、重复包、冷却、能量不足、无效目标、卸载区块、死亡、换维度、重连、多人和可选依赖缺失 |
| 扩展性 | 四系和外部模组通过稳定标签、数据、状态键或小型 API 接入，不复制内部实现 |
| 性能与配置 | 有扫描频率、目标上限、网络同步边界和可调数值；不做无界 tick 扫描或粒子刷屏 |
| 验证证据 | 至少有构建、资源/jar 检查；按系统补专服、客户端资源、GUI 预览、玩法、存档、联动或性能证据 |

命令政策：正常玩法只能通过物品、方块、菜单、服务端动作服务、NeoForge 事件和结构化网络包执行。`/temple` 仅为管理员结构调试外壳，不承载真实玩法逻辑。

## 二、六个纵向闭环

### A. 战斗、相位与主动道具

玩家闭环：获得装备或道具 -> 看懂成本与动作 -> 服务端验证并启动动作 -> 命中/位移/状态真实生效 -> 清晰反馈 -> 冷却、失败或状态结束后正确恢复。

当前基础：三件武器动作、三个相位状态、虚无能量、屏障、魂盾、停滞、裂隙、战意、魂潮、标记和主要 Curios 事件已接线；终端按键已使用自定义 payload。相位恢复解析器已有 5 个纯逻辑回归测试。

完成门槛：

- 每个动作有稳定 id、前摇、生效帧、收招、成本、冷却、打断、目标规则和单次命中集合。
- 相位在登录、退出、死亡、克隆、换维度、切换模式和效果结束时恢复原飞行、重力、碰撞与隐身状态。
- 原版夜视、发光或虚弱只作为明确写出的辅助表现，不承担旗舰效果。
- 为相位、武器、屏障/魂盾、免死、停滞和多饰品叠加建立可重复的服务端测试夹具或 GameTest 等价检查。
- 完成第三人称动作状态同步、模型姿态、专属音效和客户端最终视觉复核。

状态：**部分实现**。Java、资源与构建证据存在，完整玩法和表现证据不足。

### B. 虚空宝库与终端

玩家闭环：制作宝库 -> 放置并取得所有权 -> 相邻合并 -> 存取和聚合操作 -> 绑定终端 -> 远程打开 -> 搜索/排序/合成/常加载 -> 从权限、容量或离线错误中恢复。

完成门槛：

- 服务端拥有网络扫描、所有权、槽位聚合、存取事务、常加载票据和破坏保护状态。
- 同类物品对玩家表现为一项，但底层跨槽扣取、放入、合成与回滚必须原子化，不能复制或吞物。
- 左键、右键、Shift 快移、搜索、排序、滚动、JEI 拖入和合成区在小分辨率都可操作。
- 常加载关闭确认、异主网络、未加载区块、失效绑定、网络过大和重复请求都有短提示与修复路径。
- 建立宝库网络正常、满仓、异主、跨区块、断开、重连、连点和自动化存取夹具。

状态：**部分实现**。核心网络和界面已接线；聚合插入/取出已有事务规划器和 5 个回归测试，并修复超大堆、数字键复制、失效菜单与批量设置回滚。完整客户端交互和自动化回归证据仍不足。

### C. 虚无能量与传输

玩家闭环：产能 -> 缓存 -> 装备/饰品共享 -> 线路传输 -> 祭坛或主动能力消费 -> 从堵塞、断路、能量不足和错误方向中恢复。

完成门槛：

- 统一能量源、上限、同步、优先级和存档语义；护甲、饰品、方块和祭坛不得各自维护冲突数值。
- 传输核心支持朝向、物品/流体/能量模式、过滤、优先级、红石控制和可读阻塞原因。
- 所有产出、容量、吞吐、范围、损耗和消耗进入配置或数据定义，并有安全默认值。
- 低频扫描、缓存网络和目标上限有明确性能预算；不每 tick 全范围查找。
- 建立产能不足、容器已满、方向错误、过滤拒绝、区块卸载和重复自动化输入夹具。

状态：**部分实现/传输配置已接线**。已有产出、缓存、玩家共享与基础消费；传输核心现具备定向输入/输出、资源模式、综合优先级、九格白黑名单、红石策略、原版风格配置界面、阻塞诊断、配置化吞吐和旧存档迁移，并新增 7 个策略与 3 个布局回归测试。真实流体容器、多个核心竞争、旧存档、客户端界面、能量网络拓扑与运行时性能证据仍不足。

### D. 归零祭坛与四系成长

玩家闭环：从圣典发现结构 -> 收集最低阶资源 -> 正确搭建 -> 放入材料 -> 预览可执行结果与成本 -> 仪式动作 -> 获得产物 -> 进入虚无/虚空/混沌/深渊的下一步。

完成门槛：

- 祭坛配方从硬编码升级链迁移为数据驱动仪式，包含系别、结构等级、输入、催化物、能量、时间、输出和失败原因。
- 四系共享基础仪式接口，但目标、风险、资源与表现不同，不能只换名称和颜色。
- GUI 展示结构缺口、材料、能量、预计结果、执行阶段和输出阻塞；圣典和 JEI 使用同一数据源。
- 仪式扣费与产出在服务端关键帧原子提交；中断、拆结构、退出和输出满时不吞材料。
- 每系先完成一条代表性小闭环，再扩充数量。

状态：**部分实现/数据底座已接线**。三级结构和七条归零升级链已使用注册配方类型；服务端执行、统一阻塞状态、菜单预览、官方配方同步、圣典动态页和 JEI 共用该数据源，并有定义门禁和 7 个策略测试。四系催化、执行阶段、中断回滚、风险差异及运行时证据仍未闭合。

### E. 圣殿、生物、交易与探索

玩家闭环：发现结构 -> 识别居民状态 -> 选择交易、探索、警戒或仪式挑战 -> 读取动作与危险 -> 获得与阶段匹配的资源 -> 返回设施和成长线。

完成门槛：

- 神龛、圣殿、圣殿群拥有不同房间、角色、奖励和动线，不是同一几何体缩放。
- 五阶生物至少区分和平、交易、警戒、敌对和仪式状态，并有不同动作、AI、模型层级与声音。
- 中立角色的核心资源不能只靠无提示击杀获得；提供交易、探索、仪式或敌对变体等一致入口。
- 结构生成严格受 piece 边界、合法落点和新区域测试约束；生物生成、掉落和交易与圣典一致。
- 建立每种结构的固定测试种子/夹具和每个生物状态的可重复触发方式。

状态：**部分实现/三种结构与五阶居民首批机制已接线**。神龛承担发现与和平起步；中型圣殿承担交易、补给和II级仪式；圣殿群承担高阶设施、遗物和圣者挑战。居民五态、信众退避、随行者拦截与低血友军投射物护卫、令使近身折返/投射物偏转/裂界指向、守区与结队反击已接线；大令使具备禁域、传送成本、召回和护盾；圣者具备完整请战契约、抹除线和缺失区域。圣者低生命阶段、地形适配、结构变体和运行时证据仍未闭合。

### F. 指南、可选联动与公共扩展面

玩家闭环：低成本获得《虚无圣典》 -> 按当前进度看到下一步 -> 从物品/方块/界面跳到对应说明 -> 可选模组存在时看到联动，不存在时仍有完整核心路线。

完成门槛：

- 圣典只描述已实现内容，核心、可选和计划内容明确分层；配方、结构图和服务端谓词来自同一真值源。
- JEI、Waystones 和 Curios 分别具备存在检查、无依赖回退、版本契约、失败提示和组合测试。
- 为未来常见模组联动提供稳定标签、查询/状态接口或数据契约，不暴露内部类，不把其他模组内容写进核心原版文档。
- GUI、圣典、提示和诊断面向非技术玩家；开发术语只进调试页或日志。
- 提供一个最小示例联动和自动检查，证明外部扩展无需复制本模组规则引擎。

状态：**部分实现**。圣典和三项联动已有入口，公共扩展契约与完整组合证据不足。

## 三、优化后的执行顺序

1. **P0 真实性与权威性**：完成命令无关动作入口审计、状态恢复、重复执行防护、原子扣费和文案真值同步。
2. **P0 回归底座**：增加资源引用、语言键、命令路由、payload schema 和关键状态的自动检查；为 A/B 两个系统建立首批夹具。
3. **P1 闭合宝库与能量**：先完成 B，再完成 C；这两者是终端、祭坛、装备和联动的共享基础。
4. **P1 数据驱动祭坛**：完成 D 的一个四系代表性闭环，不同时铺开几十个新配方。
5. **P2 重做探索闭环**：三种结构、圣者请战契约和首批两项专属招式完成后，优先做全动作运行时回归，再补圣者低生命阶段、剩余生物动作、地形适配和结构夹具。
6. **P2 统一表现**：每完成一个闭环，同批完成模型、动作、粒子、音效、GUI、圣典和最终尺寸资源审查，不留“以后统一补美术”的债。
7. **P3 可扩展联动**：从已闭合的宝库、能量、祭坛和查询状态提炼稳定 API/标签，并提供示例适配。

## 五、完成声明规则

- `已接线`：注册、状态、事件/服务和资源存在，构建通过。
- `已验证`：对应服务器、客户端、玩法、存档或联动证据已完成。
- `完成`：适用质量契约全部满足，没有未经用户批准的占位或延期层。
